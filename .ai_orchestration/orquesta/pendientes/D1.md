# Tarea: D1 — Comprobantes en almacenamiento S3 (MinIO en Docker, R2 en producción)

## Contexto
La API del portal (C3c) está lista salvo **subir el comprobante**, que necesita almacenamiento de archivos. Leé `docs/adr/0012-archivos-en-r2-con-urls-firmadas.md`, `docs/arquitectura/almacenamiento.md` §4 y `docs/arquitectura/secuencias.md` §2. El código es el mismo para MinIO (Docker, servicio `minio` y bucket `comprobantes` de E1a) y para Cloudflare R2 (producción): las dos hablan S3.

**Reglas de siempre:** tests primero (mostrá la salida fallando), no hagas commit, nada de reglas de negocio en las vistas.

## Decisiones de diseño
1. **El archivo nunca pasa por Django.** El navegador lo sube directo al almacenamiento con una **URL firmada de tipo POST con política** (`generate_presigned_post`), no un PUT común: la política impone en el propio almacenamiento `content-length-range` de 1 byte a 10 MB, el `Content-Type` exacto y la `key` exacta. Vence en 5 minutos.
2. **Cada subida queda atada a quien la pidió.** Un modelo `UploadIntent` (`file_key` único, `user`, `occupancy` objetivo, `content_type`, `size_bytes` declarado, `expires_at`, `consumed_at`). Al enviar el comprobante, el `file_key` tiene que ser de un `UploadIntent` **del mismo usuario**, vigente y sin consumir. Así nadie puede reclamar como propio el archivo de otro.
3. **El backend verifica el archivo antes de aceptarlo:** que exista (`head_object`), que el tamaño real esté entre 1 byte y 10 MB y coincida con el declarado, el tipo real por **magic bytes** (leé los primeros bytes con `Range`: JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`, PDF `%PDF-`, WebP `RIFF....WEBP`, HEIC con `ftyp` + `heic`/`heix`/`mif1`/`msf1` en el byte 4) y el **sha256**, calculado leyendo el objeto en partes. Si algo no coincide: se borra el objeto, se marca el intento como consumido y la respuesta es 400.
4. **El nombre del objeto** es `receipts/<organization_id>/<uuid4>`; el nombre original del archivo no se usa en la ruta (se guarda aparte, como dato, para mostrarlo).
5. **Ver el archivo:** URL firmada de tipo GET de 5 minutos, generada solo si quien la pide tiene alcance sobre el comprobante (el empleado de su organización o el propio residente). `Content-Disposition: inline` para imágenes y PDF.
6. **URL interna y URL para el navegador.** En Docker, Django llega a MinIO por `http://minio:9000`, pero el navegador por `http://localhost:9000`. Configurá `S3_ENDPOINT_URL` (interna) y `S3_PUBLIC_ENDPOINT_URL` (con la que se firman las URLs que van al navegador). En producción (R2) pueden ser iguales.

## Endpoints
| Ruta | Quién | Qué hace |
|---|---|---|
| `POST /api/v1/portal/occupancies/{id}/receipts/upload` | residente | `{content_type, size_bytes, filename}` → valida tipo y tamaño, crea el `UploadIntent` y devuelve `{file_key, url, fields}` para el POST directo |
| `POST /api/v1/portal/receipts` | residente | `{file_key, declared_amount, transfer_date, allocations: [{occupancy_id, amount}], note}` → verifica el intento y el archivo (decisión 3) y llama a `submit_receipt`. Montos como string |
| `GET /api/v1/receipts/{id}/file` | empleado | `{url}` firmada de 5 minutos |
| `GET /api/v1/portal/receipts/{id}/file` | residente | lo mismo, solo para sus comprobantes |

Además, un comando `cleanup_orphan_uploads` que borra del almacenamiento los objetos de intentos vencidos y no consumidos (más adelante lo corre Celery; en D2).

## Tests
Con `moto` (S3 simulado en memoria): **la CI no tiene MinIO**.
1. Flujo completo: pedir la URL, "subir" el objeto con el cliente S3 simulado, enviar el comprobante → `Receipt` `pending` con `file_sha256` correcto y el intento consumido.
2. Tipo no permitido, más de 10 MB y tamaño 0 → 400 al pedir la URL.
3. **Archivo que miente:** se declaró `image/png` pero los bytes son de un `.exe` o de un texto → 400 y el objeto se borra.
4. Tamaño real distinto del declarado → 400.
5. `file_key` de **otro usuario**, ya consumido, vencido o inexistente → 400 sin crear el comprobante (y sin revelar si el archivo existe).
6. Aislamiento: ver el archivo de un comprobante de otra organización o de otro residente → 404; el empleado de la organización y el propio residente → 200 con una URL que vence en 5 minutos.
7. `cleanup_orphan_uploads` borra solo lo vencido y no consumido.
8. Un test de integración **opcional** contra el MinIO de Docker, marcado (`@pytest.mark.minio`) y salteado por defecto, que se corre a mano con `pytest -m minio`. **No** cuenta para el chequeo de "sin tests salteados" de la CI: configurá el marcador para que la CI lo excluya explícitamente (`-m "not minio"`) en vez de saltearlo.

## Cómo verificar (pegalo en el reporte)
1. Los tests fallando primero; después la suite completa en verde con el conteo total.
2. La prueba manual contra MinIO de verdad: `docker compose up -d minio minio-init` y `pytest -m minio` (pegá la salida).
3. `spectacular --validate` sin errores.
4. **Pendiente de E1a:** las imágenes oficiales de MinIO ya no se publican y E1a usa réplicas de Rancher de 2023. Investigá una alternativa S3 mantenida y compatible (por ejemplo SeaweedFS, Garage o la versión que publique MinIO en otro registro) y **recomendala en el reporte, sin cambiarla**: la decide Claude.
