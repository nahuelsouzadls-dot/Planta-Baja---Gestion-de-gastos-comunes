# Tarea: A1 — Backoffice del dueño del SaaS (por etapas)

## Contexto
Pedido de Nahuel (2026-10-28): una pantalla para él como dueño de Planta Baja, separada del panel de las administradoras. Hoy existe el admin de Django en `/admin/` con `Organization`, `OrgMembership`, `User`, edificios, ledger y auditoría registrados; `Organization` solo tiene `name`, `tax_id`, `email`.

Depende de **R1** (roles: el alta de cliente crea su primer `owner`).

## Reglas (todas las etapas)
- **Separado del panel de clientes**: el panel (`/panel`) es de las administradoras; el backoffice es solo para `User.is_superuser` (o un flag `is_platform_staff`). Ningún endpoint del panel lo habilita.
- **Doble factor** obligatorio para quien entre al backoffice (etapa 2; en etapa 1, contraseña fuerte + `/admin/` con URL no obvia vía variable de entorno).
- **Nunca se tocan números de un cliente desde el backoffice**: `LedgerEntry`, `Receipt`, `Settlement` quedan **solo lectura** en el admin (sin add/change/delete). Las correcciones las hace el cliente con un ajuste.
- **Todo queda auditado**: altas, suspensiones, cambios de plan e inicios de "ver como" van a `AuditLog` con el usuario del backoffice.

## Etapa 1 — ahora (1 cliente)
Sin pantallas nuevas; Django admin + un comando.
- `manage.py create_client --name "Confort S.A." --tax-id ... --email ... --owner-email ... --owner-first-name ... --owner-last-name ...`
  → crea la `Organization` y una `Invitation` de empleado con rol `owner` (R1); imprime el link de aceptación (hasta que D3 mande mails). Idempotente por `tax_id`/nombre: si ya existe, avisa y no duplica.
- Admin de Django:
  - `Organization`: columnas nombre, RUT, edificios, unidades, usuarios activos, creada; búsqueda por nombre/RUT.
  - Inlines de `OrgMembership` (rol, activo) dentro de la organización.
  - Ledger, comprobantes y liquidaciones en **solo lectura** (verificar y forzar `has_add/change/delete_permission = False`).
  - `ADMIN_URL` configurable por entorno (default `admin/`).
- Tests: el comando crea org + invitación owner; correrlo dos veces no duplica; el admin no permite editar `LedgerEntry`.

## Etapa 2 — con 3 a 5 clientes
Consola propia (React, ruta `/plataforma`, mismo build, acceso por rol en Django como hoy panel/portal).
- `Organization` suma: `status` (`trial` · `active` · `suspended`), `plan` (texto o FK simple), `paid_until` (fecha), `notes` (soporte).
- **Clientes**: tabla con nombre, estado, plan, edificios/unidades/usuarios, última actividad (último login de cualquier miembro, último comprobante validado), `paid_until` resaltado si venció.
- **Ficha de cliente**: datos, equipo (miembros e invitaciones, reenviar), auditoría reciente, acciones **Suspender / Reactivar** (suspendido: el panel y el portal muestran un aviso y quedan en solo lectura; los residentes siguen viendo su cuenta).
- **Alta de cliente**: el mismo flujo del comando, en pantalla.
- Facturación **manual**: registrar "pagó hasta" y un historial simple de cobros.
- Doble factor (TOTP) para usuarios de plataforma.
